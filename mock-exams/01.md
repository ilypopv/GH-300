## 1. A software developer wants to configure their local `zsh` environment so that they can invoke GitHub Copilot CLI command suggestions and explanations using the shorthand aliases `ghcs` (Copilot Suggest) and `ghce` (Copilot Explain). Which command should the developer add to their `~/.zshrc` configuration file?

`GitHub Copilot Plans and Features`

- [ ] `echo 'eval "$(gh copilot config --shell zsh)"' >> ~/.zshrc`
- [x] `echo 'eval "$(gh copilot alias -- zsh)"' >> ~/.zshrc`
- [ ] `echo 'alias ghcs="copilot suggest" && alias ghce="copilot explain"' >> ~/.zshrc`
- [ ] `echo 'gh copilot setup --alias zsh' >> ~/.zshrc`

<details>
<summary>Explanation</summary>

**Correct**

- **echo 'eval "$(gh copilot alias -- zsh)"' >> ~/.zshrc** — The `gh copilot alias -- <shell>` command is the official mechanism provided by the GitHub CLI Copilot extension (`gh-copilot`) to generate shell alias wrappers. Running `gh copilot alias -- zsh` outputs the shell-specific alias scripts defining `ghcs` (`gh copilot suggest`) and `ghce` (`gh copilot explain`). Wrapping this command inside `eval "$(...)"` within the `~/.zshrc` profile ensures these aliases are dynamically evaluated and loaded into every new zsh session.

**Why the others are wrong**

- **echo 'eval "$(gh copilot config --shell zsh)"' >> ~/.zshrc** — The command `gh copilot config` is used strictly to configure extension preferences, such as opting in or out of telemetry collection. It does not accept a `--shell` flag and does not generate alias definitions.
- **echo 'alias ghcs="copilot suggest" && alias ghce="copilot explain"' >> ~/.zshrc** — This attempts to alias the standalone GitHub Copilot CLI executable (`copilot`) rather than the GitHub CLI extension (`gh copilot`). Furthermore, manual aliases do not set up the necessary shell trap functions and execution wrappers that `gh copilot alias` automatically provides.
- **echo 'gh copilot setup --alias zsh' >> ~/.zshrc** — There is no `setup` sub-command in the `gh copilot` extension; aliases must be configured using the `alias` sub-command with the `-- <shell>` syntax.

**References**

- <https://docs.github.com/en/copilot/using-github-copilot/using-github-copilot-in-the-command-line>

</details>

## 2. A DevOps engineer is scripting a release pipeline and needs assistance constructing a Git command to cherry-pick a range of commits without committing immediately (`--no-commit`). Which command should the engineer execute?

`GitHub Copilot Plans and Features`

- [x] `gh copilot suggest -t git "cherry-pick commit range without committing"`
- [ ] `gh copilot explain -t git "cherry-pick commit range without committing"`

<details>
<summary>Explanation</summary>

**Correct**

- **gh copilot suggest -t git "cherry-pick commit range without committing"** — The `gh copilot suggest` sub-command accepts the `-t` (or `--target`) flag to specify the execution target for the suggestion. The three supported target values are `shell` (generic bash/zsh/sh commands, which is the default), `gh` (GitHub CLI commands), and `git` (Git version control commands). Specifying `-t git` scopes the language model prompt specifically to Git operations.

**Why the others are wrong**

- **gh copilot suggest --target=github "cherry-pick commit range without committing"** — The valid target name for GitHub commands is `gh`, not `github`. Furthermore, the engineer is seeking a Git command (`git cherry-pick`), not a GitHub CLI command.
- **copilot suggest -c git "cherry-pick commit range without committing"** — The standalone GitHub Copilot CLI executable (`copilot`) does not use `suggest -c git`. The `-t` target flag is a specific argument of the `gh copilot` extension.
- **gh copilot explain -t git "cherry-pick commit range without committing"** — The `explain` sub-command is designed to take an existing command string as input and explain its functionality. It does not generate new command suggestions from natural language prompts.

## 60. An engineering team wants to maximize developer productivity and maintain high test coverage across their codebase using GitHub Copilot in Visual Studio Code. Which two practices represent recommended, official workflows for creating and maintaining unit tests? (Select two)

`Developer Productivity and Testing` · `select 2`

- [x] Use ghost text autocompletion inside an existing test file to rapidly expand test coverage with new test cases that replicate established patterns and assertions
- [x] Use Copilot Chat in Agent mode to generate initial test suites, execute the tests via terminal commands, and iteratively apply fixes to failing tests
- [ ] Replace runtime test frameworks entirely by embedding natural language comments, allowing Copilot to validate code without executing assertions
- [ ] Configure GitHub Actions to automatically suppress failing test exit codes when Copilot-generated code is detected in a commit
- [ ] Use `/doc` to convert unit test files into production configuration templates

<details>
<summary>Explanation</summary>

**Correct**
- **Use ghost text autocompletion inside an existing test file to rapidly expand test coverage with new test cases that replicate established patterns and assertions** — Once an existing test file contains a few complete test cases, ghost text autocompletion detects the established structure (such as Arrange-Act-Assert, fixture usage, and naming conventions). Typing a descriptive comment or method name allows developers to rapidly add edge case tests with high consistency.
- **Use Copilot Chat in Agent mode to generate initial test suites, execute the tests via terminal commands, and iteratively apply fixes to failing tests** — Agent mode has the autonomy to create or update test files, run CLI test execution commands, inspect failure outputs, and iteratively propose fixes until the tests compile and pass, all within a developer-supervised workflow.

**Why the others are wrong**
- **Replace runtime test frameworks entirely by embedding natural language comments, allowing Copilot to validate code without executing assertions** — Unit testing requires deterministic runtime execution of assertions against running code; an LLM reading comments cannot replace automated test runners.
- **Configure GitHub Actions to automatically suppress failing test exit codes when Copilot-generated code is detected in a commit** — Suppressing test failures compromises code reliability, security, and quality, violating Microsoft and GitHub Responsible AI principles.
- **Use `/doc` to convert unit test files into production configuration templates** — `/doc` generates documentation comments for code; it does not convert test files into production templates.
